## The Docker stack

**The installation guide is the [root README](../README.md).** Clone, run `./setup.sh`, create
the first administrator, configure through the web interface. This file only covers what is
specific to the container: what runs, where it calls out to, and how an installation made with
the previous stack (TheHive, MISP) is brought to this one.

> This file used to be a second, full installation guide inherited from upstream. It
> contradicted the root README on almost every step — it cloned the upstream repository, told
> you to edit `configuration.json` by hand, and sent you to `http://localhost:8080` when the
> interface is HTTPS-only. Two guides that disagree is what makes a repository hard to
> install, so the flow now lives in one place.

### What runs

| Service | Port | Image | Role |
|---|---|---|---|
| **vhost** | **443 (HTTPS), 80** — the only published ports | `bluephish-vhost`, nginx | public TLS 1.2/1.3, security headers, Let's Encrypt challenge |
| **frontend** | none | `bluephish-frontend`, nginx | proxies everything (`/static` included) to the API over internal TLS, verifying it against the internal CA |
| **bluephish** | none | `bluephish`, built from `../app` | the API: Flask, the analysis |
| **db** | none | `postgres:17-alpine`, pinned by digest | PostgreSQL: users, history, reclassifications, verdict memory, the vault |

Networks: `edge` (vhost ↔ frontend), `backend` (frontend ↔ API, `internal: true`), `data`
(API ↔ database, `internal: true`) and `egress` (the API alone, for the mailbox, analyzers and
LLM). The vhost cannot reach the API, and only the API reaches the database. The ports
are published on `127.0.0.1` by default, as the old 8080 was; to open them to the network (and
for Let's Encrypt, which needs port 80 from the internet) set `BLUEPHISH_BIND=0.0.0.0` in
`docker/.env`. `BLUEPHISH_HTTPS_PORT` / `BLUEPHISH_HTTP_PORT` change the host ports.

The database is PostgreSQL in its own container (`db`), with its data in `vol/postgres/`. Its
password is a file, `secrets/db.password`, generated by `../setup.sh`; the database reads it as
`POSTGRES_PASSWORD_FILE` and the API as `BLUEPHISH_DB_PASSWORD_FILE`, never as an environment
variable. Certificates live in `vol/certs/` (managed by Configurações → Certificados).

**Upgrading from SQLite.** Run `../setup.sh` (it creates `secrets/db.password` and touches nothing
else), then `docker compose up -d --build`. On the first start the API copies
`vol/thephish_data/thephish.db` into the empty PostgreSQL in one transaction, keeps a copy of
the file as `thephish.db.pre-postgres-<date>.bak` and writes `thephish.db.migrated` so it never
copies twice; the old file is left untouched. If the copy fails nothing is written and the API
does not start (`docker logs bluephish` says why). Back up `vol/postgres/` from now on, or
`docker compose exec db pg_dump -U bluephish bluephish > backup.sql`.

**Upgrading from the single container.** `docker compose up -d --build --remove-orphans`. The
panel moves from `https://localhost:8080` to `https://localhost`; set `BLUEPHISH_BASE_URL` to the
public `https://` origin of the vhost if you use SSO (the redirect URI changes). On first start
the API generates the internal CA, its own certificate and a self-signed vhost certificate; the
vhost and the frontend wait for those files. A reverse proxy you already had in front now sits in
front of the vhost and goes into `BLUEPHISH_TRUSTED_PROXIES` together with the two compose
networks (the default is `172.30.10.0/24,172.30.11.0/24`; keep both when you add one).

There is **no Cortex, no Elasticsearch, no TheHive and no MISP** in this file. The analyzers
run inside the container (`app/analyzers.py`), configured from its own **Integrações →
Analisadores** screen, and the verdict emails go out over SMTP from `app/mailer.py`. TheHive
is a destination the application can record to, like Jira, and MISP is something TheHive
exports to: both are installed apart from this stack, and
[docs/integracoes/thehive.md](../docs/integracoes/thehive.md) covers how to connect them.

A fresh installation records every analysis to **disk** (`vol/thephish_data/analises/`), the
one destination that needs nothing else. That includes the reported e-mail itself, kept until
somebody sets a retention in **Integrações → Tickets → Disco** — decide how long you want it
before the mailbox is in production.

### Where the app calls out to

The container makes outbound connections you should know about before putting it behind a
restrictive egress policy: the mailbox (IMAP or Microsoft Graph), the LLM endpoint, every
enabled analyzer vendor (and each analyst-defined analyzer), the SMTP relay, each enabled
ticket destination, Entra ID (`login.microsoftonline.com`: SSO sign-in and the app tokens for
Graph, EOP and MDTI), the blocking destinations (EOP at `outlook.office365.com`, the
firewalls), the syslog server that receives the audit copy, every generic connector and
volume-alert webhook, and — by design — hosts named inside reported emails: each hop of a
shortened link and, when an email is rendered, its remote images.

The public feeds (Integrações → Analisadores) download their lists in the background from
two fixed hosts, over HTTPS and without following redirects: `hole.cert.pl` (CERT Polska, the
recommended pack) and `raw.githubusercontent.com` (Phishing.Database, only if an administrator
turns those feeds on). Nothing is downloaded until an administrator turns a feed on. If you restrict egress, allow those two names or leave the
feeds off; an analysis never calls them, it reads the local copy under
`data/feeds/`.

The services are switched on and given credentials in the interface. The Microsoft and vendor
endpoints are fixed in the code (`imap.gmail.com` for the Gmail provider,
`graph.microsoft.com`, `login.microsoftonline.com`, `outlook.office365.com`, the analyzer
APIs); the LLM, SMTP, TheHive, Jira, firewall, syslog, connector and analyst-defined analyzer
addresses are the ones you type.

Two traps, both the same trap:

- A destination **in another container of the same Docker network** is reached by its service
  name, not `localhost`. Inside the container, `localhost` is the container.
- A destination **on the host machine** (a local Ollama, a self-hosted Jira, an internal
  Splunk) is reached at `host.docker.internal`, which is not mapped by default on Linux. Add
  it to the `bluephish` service in a `docker-compose.override.yml`:

  ```yaml
  services:
    bluephish:
      extra_hosts:
        - "host.docker.internal:host-gateway"
  ```

> This is also why a connector (**Integrações → Tickets**, below the built-in destinations —
> [architecture](../docs/conectores-genericos.md) ·
> [manual](../docs/conectores-manual.md)) refuses a private-network destination unless you
> tick *allow internal network*: from inside a container, "the internal network" includes the
> whole compose network and the host. The destination is re-checked on every dispatch, not
> only when you save it.

### Atualizando de uma instalação com TheHive e MISP

Vale para quem instalou enquanto o `docker-compose.yml` trazia `thehive`, `cassandra`, `misp`,
`mysql`, `redis` e `hive-ai-agent`, com a aplicação no contêiner `thephish`. Uma instalação
nova não precisa de nada disto.

O que muda para você:

- O serviço e o contêiner da aplicação passam a se chamar **`bluephish`**. Script de deploy,
  backup ou monitoramento que cite `thephish` (`docker exec thephish`, `docker logs thephish`)
  precisa ser ajustado.
- Os outros seis serviços saem do compose. A atualização **para e remove os contêineres
  deles**. Os dados ficam onde estão, em `docker/vol/`; nada é apagado do disco.
- Usuários, histórico, reclassificações, trilha de auditoria e a configuração ficam em
  `docker/vol/thephish_data/` e em `docker/thephish_conf_files/`, que não mudam de lugar.
- Se o destino TheHive está em uso, ele continua habilitado no BluePhish. Sem um TheHive
  respondendo, cada análise registra a falha desse destino e as telas de histórico avisam que
  a parte do TheHive está faltando.

**1. Decida o que fazer com o TheHive, antes de atualizar.**

- *Continuar com o TheHive que já roda aqui:* crie `docker/docker-compose.override.yml` com os
  serviços `cassandra` e `thehive`, como está em
  [docs/integracoes/thehive.md](../docs/integracoes/thehive.md#manter-os-contêineres-de-uma-instalação-antiga).
  Eles continuam no mesmo projeto e nada muda no BluePhish.
- *Deixar o TheHive:* em **Integrações → Tickets**, habilite o **Disco** e desabilite o
  **TheHive**. Pode ser antes ou depois de atualizar; enquanto o TheHive ficar habilitado sem
  um TheHive respondendo, cada análise registra a falha dele. Os casos antigos continuam nos
  dados do TheHive em `docker/vol/`, mas deixam de aparecer no painel: as telas de histórico
  leem só os destinos habilitados.

**2. Guarde uma cópia do que tem segredo.**

```bash
cp docker/thephish_conf_files/configuration.json ~/bluephish-configuration.json.bak
cp docker/thehive/application.conf ~/thehive-application.conf.bak
```

Um backup de `docker/vol/` antes de qualquer atualização continua sendo uma boa ideia.

**3. Atualize o código.** O `git pull` vai parar com *"Your local changes to the following
files would be overwritten by merge: docker/thehive/application.conf"*. Esse arquivo saiu do
repositório, e a sua cópia tem a chave que o `setup.sh` gerou. Libere **só ele**:

```bash
git update-index --no-skip-worktree docker/thehive/application.conf
git checkout -- docker/thehive/application.conf
git pull
```

Se a mensagem citar também `docker/hive_ai_agent_conf/configuration.json` (acontece quando
ele foi editado à mão), guarde uma cópia e rode `git checkout --` nele antes do `git pull`.

> **Não faça o mesmo com `docker/thephish_conf_files/configuration.json`.** Esta atualização
> não mexe nele, então o `git pull` não reclama dele. Um `git checkout` ou `git stash` nesse
> arquivo troca todas as credenciais configuradas por campos vazios, sem erro: a aplicação
> sobe e simplesmente para de analisar (§7.8 da arquitetura).

Se você vai continuar com o TheHive, devolva a configuração dele ao lugar. A pasta agora é
ignorada pelo git:

```bash
mkdir -p docker/thehive
cp ~/thehive-application.conf.bak docker/thehive/application.conf
```

**4. Suba a versão nova.**

```bash
cd docker
docker compose up -d --build --remove-orphans
```

O `--remove-orphans` é o que remove o contêiner antigo `thephish`, que segura a porta 8080, e
os contêineres dos serviços que não estão mais declarados. Sem ele o `up` falha com *"port is
already allocated"*. Com o `docker-compose.override.yml` do passo 1, `cassandra` e `thehive`
continuam declarados e não são tocados.

**5. Confira.**

```bash
docker compose ps                                   # bluephish: Up (healthy)
docker compose exec bluephish python3 manage.py list-users
```

Entre no painel e veja se os usuários, o histórico e as integrações estão lá.

**Alternativa: instalar do zero e trazer os dados.** Em vez dos passos 3 e 4, dá para parar a
stack antiga, renomear a pasta, clonar de novo e rodar o `setup.sh`. Para trazer os dados da
pasta antiga para a nova, com o contêiner parado (em servidor onde o Docker é só do root,
ponha `sudo` nos comandos `docker`):

```bash
cd docker
docker compose down
sudo cp -a ../../Bluephish.antigo/docker/vol/thephish_data vol/
cp ../../Bluephish.antigo/docker/thephish_conf_files/*.json thephish_conf_files/
docker compose up -d
```

`vol/thephish_data` traz os usuários, o histórico, a trilha de auditoria e o certificado; os
dois `.json` trazem as credenciais e a whitelist. A configuração antiga volta com o destino
TheHive habilitado e o Disco desligado: acerte isso em **Integrações → Tickets**, como no
passo 1.

**6. O que sobra no disco.** As pastas dos serviços removidos ficam em `docker/vol/`
(`cassandra-data`, `data`, `index`, `mysql`). Apague-as à mão quando tiver certeza de que não
precisa mais delas; nenhum comando deste repositório faz isso por você. As variáveis
`THEHIVE_APIKEY`, `LLM_API_ENDPOINT`, `LLM_MODEL_NAME` e `WEBHOOK_SECRET` do `docker/.env`
deixaram de ser lidas e podem sair.

### Testar a metodologia de score no container

O código da aplicação é copiado para dentro da imagem (`COPY . /root/thephish/`
no `app/Dockerfile`), então **depois de um `git pull` é preciso reconstruir** —
um `restart` sobe a imagem antiga:

```bash
docker compose build bluephish && docker compose up -d bluephish
```

Nada além disso é necessário. `scoring.py` e `spam_headers.py` usam só a
biblioteca padrão, então `app/requirements.txt` não ganhou nenhum pacote (§7.2 da
arquitetura: dependência nova ali é o que quebra esta imagem).

A seção `scoring` do `configuration.json` também não precisa ser criada à mão. A
configuração é mesclada sobre os padrões, então uma instalação que nunca a
tocou já roda com phishing ≥ 50, suspeito/spam ≥ 40 e legítimo ≥ 20; a seção é
gravada na primeira vez que alguém salvar em **Integrações → Priorização**. Isso
importa porque esse arquivo é `skip-worktree` e carrega as chaves reais (§7.8):
ele não é atualizado pelo `git pull`, e não precisa ser.

**Ver os pesos que estão valendo:**

```bash
docker compose exec bluephish python3 manage.py weights
```

**Pontuar um `.eml` sem rede, sem cota de fornecedor e sem TheHive:**

```bash
docker compose exec bluephish python3 manage.py score samples/newsletter.eml \
    --analyzer virustotal=safe
```

Os cabeçalhos são lidos do arquivo de verdade — autenticação e gramática de
lista; o nível de cada analisador entra como argumento, o que permite calibrar
peso sem gastar uma análise real por tentativa. A saída traz a memória de
cálculo inteira: peso, fator e contribuição de cada linha, e por que quem não
participou não participou. `--json` para consumir em script.

Três amostras acompanham a imagem em `samples/` (`samples/README.md` explica o
que cada uma demonstra). O par que vale rodar junto:

```bash
docker compose exec bluephish python3 manage.py score samples/newsletter.eml --analyzer virustotal=safe
docker compose exec bluephish python3 manage.py score samples/phishing.eml   --analyzer virustotal=safe
```

As duas trazem `List-Unsubscribe`. A primeira sai como `spam` e some da fila; a
segunda não, porque o domínio dela não passou no DMARC — e é o servidor de
entrada que escreve isso, não quem mandou a mensagem.

**Um `.eml` seu:**

```bash
docker compose cp suspeito.eml bluephish:/tmp/suspeito.eml
docker compose exec bluephish python3 manage.py score /tmp/suspeito.eml \
    --analyzer virustotal=malicious --llm High
```

**A suíte de testes, dentro da imagem que vai rodar:**

```bash
docker compose exec --workdir /root/thephish bluephish python3 -m unittest discover -p "test_*.py"
```

Não toca a rede e não escreve na árvore. É a mesma suíte que o CI roda, aqui
contra o Python 3.14 e as versões que a imagem de fato carrega — que é o que
`app/requirements.txt` documenta e o que o CI não consegue provar sozinho.

**Na interface**, depois de reconstruir: *Integrações → Priorização* traz o
ranking de fatores com o peso editável na linha, e *Phishing confirmado* traz a
faixa tática. Os painéis que dependem das tags novas (`score:`, `tier:`,
`auth:`) só enchem com análises feitas a partir desta versão — casos antigos
aparecem como "não pontuado", nunca como zero.

### Notes

**IP de origem na auditoria (`172.18.0.1`).** Se a tela de Auditoria mostra o gateway da rede
do Docker (`172.x.0.1`) em vez do IP de quem entrou, o endereço real se perdeu *antes* de chegar
ao BluePhish — nada no aplicativo consegue recuperá-lo. A trilha marca esses registros com
`ip_origem=gateway-docker (IP real indisponivel)`. O que decide isso é como a porta chega ao
contêiner:

| Acesso | O que o BluePhish enxerga | O que fazer |
|---|---|---|
| Porta publicada com DNAT do iptables (padrão do Docker, daemon com `iptables` ligado) | O IP real | Nada |
| Porta publicada pelo proxy em userland do Docker (`docker-proxy`) | O gateway `172.x.0.1` | Em `/etc/docker/daemon.json`: `{"userland-proxy": false}` e reiniciar o Docker (exige `iptables` habilitado) |
| Serviço `bluephish` com `network_mode: host` | O IP real | Troca o `ports:` por `network_mode: host` no compose; o painel passa a ouvir direto no host |
| Túnel (`ssh -L`, `socat`, port forwarding) | O IP local do túnel, sempre | Não tem correção: o túnel termina a conexão na máquina dele |
| Proxy reverso na frente (Nginx, Caddy, Cloudflare) | O IP do proxy | O proxy envia `X-Forwarded-For`, e o IP do proxy entra em `BLUEPHISH_TRUSTED_PROXIES` (CIDRs separados por vírgula) |

`X-Forwarded-For` só é honrado quando o par é um proxy listado em `BLUEPHISH_TRUSTED_PROXIES`
(padrão: só o loopback), e vale a entrada mais à direita que não é proxy. Antes, a primeira
entrada era aceita de qualquer origem e quem acessasse direto podia escolher o IP registrado.
**Mudança de comportamento:** quem já roda atrás de proxy reverso precisa listá-lo em
`docker/.env` (`BLUEPHISH_TRUSTED_PROXIES=172.18.0.0/16`, por exemplo). Sem isso, todos os
clientes passam a ter o IP do proxy — na auditoria e no limitador de tentativas de login, que
conta por IP: com cinco tentativas por minuto compartilhadas, um cliente só já trava o login de
todos. Uma entrada mal digitada é ignorada e registrada no log (`docker logs bluephish`).

O mesmo vale, e pior, para o **banimento de IP** (Configurações → Segurança): com todos os
clientes aparecendo como o IP do proxy, o primeiro banimento tranca todo mundo de fora. A aba
Segurança avisa quando a sua requisição chegou com `X-Forwarded-For` de um endereço que não está
na lista. O gateway do Docker (`172.x.0.1`) e o próprio proxy sem cabeçalho nunca são banidos.
Os banimentos ficam na memória do processo: `docker compose restart bluephish` solta todos.

**Cofre de segredos — atualizando uma instalação existente.** O compose agora monta a pasta da
chave mestra do cofre (`docker/secrets/`, somente leitura). Sem a chave o contêiner sobe assim
mesmo, com os segredos em texto como antes, e a aba Segurança avisa. Para ligar o cofre, rode
`../setup.sh` (gera a chave se ela não existe e não mexe no resto) ou gere à mão:
`mkdir -p secrets && (umask 077; openssl rand -base64 32 > secrets/master.key)`. Na subida, a
aplicação passa os segredos do `configuration.json` para o banco, cifrados; o arquivo fica só
com referências. **Guarde uma cópia da chave fora de `docker/vol/`** — sem ela os segredos não
abrem, e um backup do volume sozinho não os recupera (é de propósito). `THEPHISH_SECRET_KEY`
pode sair do `.env`: a aplicação gera e guarda a dela (tirar a variável desloga todo mundo uma
vez). Conferir: `docker compose exec bluephish python3 manage.py vault-status`.

**reCAPTCHA trancou o login?** (chave errada, proxy corporativo bloqueando o script do Google)
`docker compose exec bluephish python3 manage.py captcha-off` desliga e mantém as chaves; ou
`BLUEPHISH_CAPTCHA_DISABLED=1` em `docker/.env` e `docker compose up -d`.

**Firefox and the live analysis log.** On some Linux setups Firefox closes the AJAX connection
before the response arrives and garbles the WebSocket frames, which surfaces as an error
mid-analysis. Another browser is the simpler fix; to stay on Firefox, in `about:config` raise
`network.http.network-changed.timeout` from 5 to 60 and set
`network.websocket.extensions.permessage-deflate` to `false`.

> **⚠️ The certificate is self-signed.** It is generated on first start so that the session
> cookie can be issued with the Secure flag. For anything beyond a local or internal
> deployment, put a reverse proxy with a CA-issued certificate in front, set
> `BLUEPHISH_BASE_URL` and list the proxy in `BLUEPHISH_TRUSTED_PROXIES`.
